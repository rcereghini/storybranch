# Story graph and current StoryNode implementation

Status: current implementation contract and enduring `Story`/`StoryNode` invariants. Before planning changes, read [the Story system index](story-system/README.md), [canonical terminology](story-system/terminology.md) and [decisions](story-system/decisions.md). The domain terms are Story, StoryTrunk, StoryNode, StoryBranch and StoryLeaf. Every published StoryNode connects to the trunk, other nodes and/or leaves and may have several outgoing StoryBranches. The portable `StoryNode` type and shared `StoryNode` component provide data and rendering respectively. Code, UI and new stored/API contracts use these names; compatibility for prior records and clients is isolated at the boundary. This does not restore the removed prototype wire format. Current and target behavior are distinguished in [the October 23 review](story-system/current-state-review.md).

## Required contract for every StoryNode type

Battle is now supported in private mixed drafts and previews through [S35l](story-system/battle.md#s35l-persisted-battle-graph-authoring). It consumes typed boolean preemptive and bounded integer attack/defense bonus inputs, resolves Attack/Guard/Escape through the battle engine, retains a pending result, and follows exactly one Win/Loss/Escape StoryBranch on explicit Continue. Real play remains server-authoritative; creator publication of any battle draft remains gated. This adds no fallback type to the ordinary edition schema.

This is a requirement for all current and future types, including RPG turn-based battles. A StoryNode type is a child renderer of `StoryNode`, never a parallel player architecture. It must declare **Input → StoryNode type → Completion event → Output(s)**. A StoryNode must lead onward or deliberately close its branch; an unexplained dead end is invalid.

| Authoring contract | Completion event | Logical outputs |
| --- | --- | --- |
| `nextStoryNode, text → Text` | Next button click | One: Next StoryNode |
| `nextStoryNode, videoUrl, videoAdvance → Video` | `auto` (default): video finished OR Next; `continue`: explicit Continue only | One: Next StoryNode; all triggers use the same server command |
| `text/videoUrl, options[A,B,C] → Text/Video with Options` | Available option chosen | Multiple authored outputs; only the chosen A/B/C is followed |
| `range, passStoryNode, failStoryNode → Dice Roll` | Roll persists a result; a separate Next button click confirms it | Two: Pass or Fail, selected from the stored result |
| `text, results[score → resultStoryNode] → Reveal` | Reveal button click | Two to twelve results; the server follows the result with the highest score, a tie going to the first listed |
| `nextStoryNode, comic{layout, panels[image, caption, alt]} → Comic` | Next button click (in a scrolling strip it follows the last panel and is never locked behind scrolling) | One: Next StoryNode; zero at an ending |
| Future battle configuration → RPG turn-based battle | Server-validated battle completion, then the type's documented confirmation event | Declared outcomes such as Win/Loss, using the same routing lifecycle |

The target catalogue below declares future contracts before implementation. Its field descriptions are typed design requirements, not fields accepted by the current schema. See [the complete type catalogue](story-system/node-types.md) for config/input/result distinctions, authority, bounds and recovery requirements.

| Target type / status | Typed input and configuration | Completion trigger | Output destinations |
| --- | --- | --- | --- |
| GraphicNovel — deferred | Ordered bounded spreads/panels, reading direction, bookmark; optional declared choice slots | Explicit Finish or chosen output; internal StoryNode turns remain on the node | One `next`, or named choice outputs, each bound to a node |
| Form — deferred | Versioned allowlisted field schemas, typed defaults and optional private response draft | Server-validated Submit; optional explicit Cancel | `submitted` and enabled `cancelled` outputs to authored nodes; invalid input stays on the form |
| TurnBasedBattle — [S35](story-system/battle.md), staged shared player; public authoring/start gated | battle-1 encounter, one enemy, run health/stats, typed preemptive and bounded attack/defense bonuses | Server persists Attack/Guard rounds or Escape and terminal result; explicit Continue | Required `win`, `loss`, `escape` routes; turn limit means loss; all destinations must safely reach a StoryLeaf |
| Advertisement — deferred | Labeled placement, provider/mode/fallback config; verified eligibility/consent projection | Verified provider completion if rewarded; otherwise explicit continue/skip; bounded unavailable handling | `completed`, `skipped`, `unavailable` to authored nodes; only verified completion can grant an approved reward |
| StoryLeaf — conceptual endpoint, currently `kind: ending` | Ending presentation/summary and story-or-branch completion intent | Committed entry closes the current run once | No authored in-story output; shared replay, parent-return and discovery exits |

ComicStrip currently maps to `comic` with `layout: "scroll"`; Comic grid uses `layout: "grid"`. Text/Video options remain explicit variants. The target typed input/output registry, result bindings, visit state and generalized typed imports remain deferred. Blank-draft authoring is implemented through StoryTrunk settings. Every new implementation must update this table and its detailed target contract together.

Concrete storage mapping: `text` is `transcript`, `videoUrl` is `video` (a shipped `/media/...` clip or `asset:<assetId>` for an uploaded clip), and `nextStoryNode` is the one direct choice's `route.targetStoryNodeId`. Options are `choices` with conditions and routes. Dice range is 1–`sides`; `target` defines passing values, and `success.targetStoryNodeId`/`failure.targetStoryNodeId` are Pass/Fail. A reveal's results are its one choice's `outcome.results`, each a namespaced `scoreId` and a route. These aliases describe authoring intent, not duplicate persisted fields.

All player APIs require `X-Story-Player: player-view-v1`; older player responses are retired, while existing persisted saves/editions/receipts remain supported. Save lists/history are projected, and direct Firestore run/receipt reads are denied by the corresponding rules. Published playback receives a server-evaluated `RenderStoryNode` and `PlayerRun` projection, described in [player runtime](story-system/player-runtime.md). Studio adapts authored configuration with its disposable full save through the same pure projection function. The older `StoryNodeInput` remains an authoring/preview shape. `StoryNodeOutput` is an intent (`choiceId`, optionally `roll`/`continue`), not permission for the browser to set a result or destination. `StoryNode` owns common output controls and dispatch; the pure domain engine and API select/persist the resulting route. Available options may depend on stats, keys/items or the latest persisted roll. Future battle outcomes must join these same authoritative condition/effect contracts.

## StoryLeaf completion and child Story return

S20 adds selected completed-run continuity to the S19 boundary. Source editions declare local boolean `runKeyExports`; imports opt into `selection: completed-run`. Players choose one owned completed run per source Story/edition, with no automatic selection. The service verifies its completion receipt, pinned edition and export permission, then stores only declared values and provenance in the sequel snapshot. Required continuity requires a selected run, while an absent key is a valid false result. Private source lists are bounded and expose ending labels/time, not inventory. See [selected-run imports](story-system/keys.md#selected-completed-run-imports-s20). S21 below adds child import consent; cross-creator sharing remains deferred.

S19 supports consented **ever-earned persistent key** imports between Stories owned by the same creator. Source editions explicitly permit destination IDs; destination editions pin source definitions and local aliases. Root starts snapshot verified grants after player approval, and `scope: import` conditions read only that server-owned snapshot. Local effects cannot forge imports. Required missing/declined imports block start; optional ones default false. S21 adds explicit child consent and source selection, scoped to the parent revision/location and exact child Story/edition; children snapshot their own imports without changing their parent. See [persistent-key imports](story-system/keys.md#persistent-key-imports-s19) for authoring, permissions, provenance and compatibility. S20 adds selected-run local facts; commercial rights remain deferred.

S18 invitation entry keys are checked transactionally before every new root or child run, including starts against older editions. Live Story-root entry policy is separate from the immutable graph and can be configured before publication. Existing runs continue; their later choices, resume and completion are not retroactively gated. Only the owner or an account with the permanent Story entry key may start when invitations are required. See [invitation semantics and media limits](story-system/keys.md#invitation-entry-contract).

S17 adds permanent per-player Story keys: StoryTrunk declares `progression` threshold rewards; committed StoryLeaf completions count once per distinct run across editions. Each new root/child run snapshots only that Story edition's declared granted keys. StoryBranch conditions use `kind: key, scope: story` to check this server-only snapshot; absent scope remains run-local. Hidden options and forged selections use the same authoritative evaluator. The completion projection may include newly earned `storyKeys`, displayed inside the shared StoryNode. Existing saves/editions are not rewritten; no historical completions are counted. See [the complete key contract](story-system/keys.md#first-implementation-persistent-story-progress).

StoryLeaves now support optional versioned `leaf` configuration: an ending summary and up to 20 labeled, unique Story-local reward keys. Committed entry grants missing keys and writes a bounded `Save.completion` receipt (version, ending ID, revision/time, summary and rewards with `newlyGranted`) with the run and event in the existing transaction. It has no command-receipt TTL. The shared StoryNode shows these saved details in Studio preview and real playback, retaining replay/discovery/parent-return controls. Reload never grants rewards. Old completed saves without receipts stay unchanged, and edits require a new edition. Approved account achievements use the separate registry described in [keys](story-system/keys.md#approved-account-achievements); entitlements remain deferred. See the [local completion contract](story-system/story-nodes.md#local-completion-contract).

Roll feedback occupies reserved space in the center of its dice StoryNode, replacing the die display without resizing the StoryNode. It remains visible after reload while awaiting Next, and disappears on leaving that StoryNode; the persisted result remains available to conditions and the story log. Transient player notifications overlay the layout rather than pushing the main content down.

Twenty-sided rolls use a lazy-loaded Three.js model inside the shared StoryNode. Roll begins a cosmetic tumble, then the model faces the saved server value. Next remains a separate action and can skip the remaining animation. Reload restores a static saved face; reduced motion disables tumbling. WebGL failure and other dice sizes use the accessible numeric display in the same reserved region. See [animated d20 presentation](story-system/node-rendering.md#animated-d20-presentation); no randomness, routing or persistence moves into the renderer.

App loading uses a fixed, centered overlay for catalogue/start/initial player requests. It does not occupy document space or intercept navigation. An already loaded player keeps its existing frame during transitions, with screen-reader loading status only. Future loading indicators must overlay content or occupy reserved space where that content belongs, never insert a banner above it.

A normal output follows a StoryBranch to another placement in the current pinned edition. Entering an ending placement (a StoryLeaf) marks the current save completed. An ordinary StoryBranch does not create or close a separate run. The common completion UI offers replay, return to the parent for a child Story, or other catalogue stories. Selecting another Story starts a separate save/context; rewards and local keys do not silently transfer. Recommendations currently use the other catalogue entries, not a personalization service. Authored direct cross-story routes are not implemented; the completion shell currently owns cross-story handoff.

Terminal StoryNodes have no *in-story* choices, but still have the common completion outputs. A future type must document all possible exits (including failure/cancel where relevant), use the shared wrapper, reject invalid output shapes and prove reload/retry behavior. This rule is also recorded in root `AGENTS.md` for future implementation work.

Stories own a versioned graph of StoryNode/StoryLeaf **placements**, currently stored as StoryNodes with an `entryStoryNodeId`. StoryBranches bind output routes between them. The target StoryTrunk is the single title/configuration root outside the playthrough; the trunk is now a typed configuration view over existing root metadata and optional `trunkContext` (version 1 starting keys). `entryStoryNodeId` identifies the first playable placement, not the trunk. Reusable StoryNode content lives independently in the StoryNode library. Each placement pins a content snapshot using optional `sourceStoryNode: {id, revision}` and adds its own entry effects, conditions, costs and output routing. Routes reference placement `targetStoryNodeId`; saves persist placement `storyNodeId`. These contracts and all routing/condition rules live in platform-independent TypeScript.

Preview and new publication compile a safe subset with creator diagnostics. Unfinished choices and unreachable placements stay in drafts but are omitted from editions; required outcomes propagate safety upstream. No safe start blocks preview/publication. The conservative policy requires an unconditional, cost-free strategy to a StoryLeaf; see the implementation section in StoryNodes. Existing editions retain their original graphs. StoryLeaf account rewards and general typed data carried by StoryBranches still need their separate authority/schema implementations. Local completion keys follow the contract above. See [StoryNodes and termination](story-system/story-nodes.md#storyleaves-and-termination).

## Independent StoryNodes and assets

Video generation (`/assets/generate`) and video editing (`/assets/edit/{assetId}`) are asset-authoring tools, not new story StoryNode types or alternative playback renderers. Their outputs are independent private library assets; creators explicitly select those assets in StoryNode placements. Both `video` and `video-options` continue to share the retained `ScenePlayer` child of `StoryNode`, with completion callbacks and output children supplying their different behavior. Generated media never changes an edition, route, or save.

Creator Studio's branching timeline is an authoring view of StoryNode placements, not a player or a new StoryNode type. It edits the existing choice route fields, including individual dice/check Pass/Fail and reveal result routes, while preserving effects and conditions. Optional draft-only `storyNodePositions` maps placement IDs to bounded finite canvas coordinates (0–50,000; at most 80 entries). It is persisted with draft revisions and excluded from immutable published manifests and saves. Moving a card cannot change playback order; only output connections do. The existing domain/publication validation and shared Story/StoryNode runtime remain authoritative.

`StoryNodeContent` declares title, transcript, text/video type, optional video/photo asset references, optional video advance mode, and named output slots (ID, label, hint). It has no story identity, destination, condition, effect or user state. The initial reusable library supports Text, Text with Options, Video and Video with Options; dice/reveal remain story placements until their reusable configuration and binding contracts are defined. `placeStoryNode` creates independent output bindings for each story. Editing one placement never changes another placement or a published edition. Content edits to a linked StoryNode must be saved as a new library revision before publication; routes can change independently. The server checks linked content against its owned immutable revision before publishing.

`POST /api/story-nodes/{id}` saves a private immutable revision with optimistic concurrency and an idempotency receipt. `GET /api/story-nodes` lists the current creator's latest revisions with cursor pagination. `POST /api/story-nodes/{id}/share` explicitly publishes the specified revision and its referenced assets under the creator publishing policy. `GET /api/shared-story-nodes/{id}/{revision}` is public only after sharing; no private draft, player or save state is returned. `/p/{id}/{revision}` is an isolated, disposable preview using the shared Story/StoryNode lifecycle. Its output slots close the preview, with Replay and Discover exits; it does not claim to follow a particular story's routes or award progress. Real story play remains server-authoritative. Sharing is currently permanent for that revision; dynamic social preview metadata and revocation are not implemented.

Assets (uploaded or generated videos and photos) are stored per creator at `users/{uid}/clips/{assetId}`, with the file at the same path in Storage. Video and photo references may be reused across any owned StoryNodes. JPEG, PNG and WebP photos are capped at 10 MB, and use `image: "asset:<id>"`; videos retain the MP4/WebM 100 MB / 60-second limits. Photo signatures, declared MIME and byte lengths are checked by the server; image duration is zero. Photos render in reading StoryNodes and as video posters. Storage rules accept only owner-created pending uploads with matching size/type. Publishing and StoryNode sharing validate asset ownership, readiness and media kind, and record each used file in the edition or shared StoryNode revision so playback never reads the creator's private records. SVG and arbitrary external media URLs are not supported.

The React `Story` provider receives the story identity, authoritative save context, and a `StoryUser` projection: identity, account stats, achievements and save spots. The current API includes the active save spot; the catalogue separately loads the player's other journeys. These are explicit application fields, not a raw Firebase user or credentials. Account stats are snapshotted at story start; local keys, items, health, milestones and roll results belong to that story instance. Verified account claims are listed privately in My adventures, separately from legacy profile strings; they are not automatically copied into every Story projection.

Every renderer is wrapped by `StoryNode`. It reads the Story context and emits a typed `StoryNodeOutput` containing a choice ID. The server resolves the authored output, validates conditions/costs and persists the destination. Clients never send a trusted destination, dice value or user stats. `StoryNodeInput` documents the portable StoryNode/context/user input shape.

| StoryNode type | Input and presentation | Outputs |
| --- | --- | --- |
| `text` | Narrative text and story context | One unconditional Next; zero at an ending |
| `text-options` | Text and conditional choices | One selected available output |
| `video` | Local video, captions and transcript | One unconditional Next; zero at an ending |
| `video-options` | Video and conditional choices | One selected available output |
| `dice` | Sides, target, context | Roll stores/displays value; Next follows Pass/Fail |
| `reveal` | Text and a list of results, each a score and an ending StoryNode | Reveal follows the highest-scoring result |
| `comic` | 4 or 9 panels in a square grid, or 4–12 in a scrolling strip; each panel an owned image, an optional caption and alt text | One unconditional Next; zero at an ending |

All seven types use the same StoryNode parent, output controls, offline/busy handling, Story context and server command path. Linear videos default to automatic advancement on completion or Next. `videoAdvance: "continue"` waits at the final frame for Continue; this field is rejected on other types. Option videos always wait for an explicit choice. The player pauses and hides the retained video element during text/dice StoryNodes, preserving playback authorization for a later video. One deterministic next video may preload unless the browser requests data saving; preload never commits a destination. The current frame remains during API/media loading, and reading StoryNodes use a short entrance transition that respects reduced motion. The player fills the viewport; native fullscreen includes its controls. Shared Button/Panel components use Tailwind utilities with existing custom theme tokens; older app surfaces retain their CSS pending gradual migration. Add a future battle renderer and validated battle outcome to this contract when implementing combat, not a simulated client-authoritative win button.

Prototype dice default: uniform integer 1–N, pass on value >= target. The API injects Node crypto randomness into the pure transition function. A draw is reused during Firestore transaction retries; the existing idempotency receipt preserves the committed result for network retries. Roll increments the save revision and records `lastRoll` with `pending: true` while staying on the dice StoryNode. Rerolling that pending result is rejected. Next consumes the persisted outcome and clears pending while moving onward. Both steps are idempotent commands; reload between them preserves the result. `lastRoll` and the story event persist the result. Authored routes may award story-specific keys; later conditions can inspect those keys or the most recent roll from a named StoryNode (`kind: roll`). Older roll history remains in the log; only the most recent roll is available directly in conditions.

## Comics

A comic StoryNode stores `comic: {layout, panels}`. `layout` is `grid` (a square of exactly 4 or 9 panels, 2×2 or 3×3) or `scroll` (4–12 panels read top to bottom). Each panel has an ID, an `image` (`asset:<id>`, an owned photo), an optional `caption` (up to 200 characters) and optional `alt` text (up to 400). Captions are rendered as text over the art (grid) or under it (strip), never baked into the image, so they stay editable and readable by screen readers. Drafts may hold 1–12 panels and panels without images; `comicIssue` in the domain is the publication rule and Studio shows its message inline. Validation rejects `comic` on any other StoryNode type, a comic StoryNode with a `video` or StoryNode `image`, a grid that is not 4 or 9 panels, a strip outside 4–12, repeated panel IDs and a panel without an image. Routing is the Text contract: one unconditional direct Next, or none at an ending.

Publication checks every panel image like a StoryNode photo (ready, owned, an image) and records it in the edition. The player API returns `panels`, the download URLs in panel order, beside `image`. Comics are not reusable library StoryNodes yet, like dice and reveal.

The cast and art style used to generate panels are draft-only (`DraftRecord.comic`, up to six characters, each a name, description and optional reference image). Like `storyNodePositions`, they never enter a published edition. See [Creator Studio](17-creator-studio.md#comics).

## Quizzes: scores and the reveal StoryNode

A personality quiz is ordinary StoryNodes. Each answer on a Text or Video with Options StoryNode carries a `score` effect (`{id, kind: "score", scoreId, delta}`) that adds points toward one result. Scores are namespaced to the story like keys and items, live in the save's `scores` map (0–999 each), and are never shown to the player. Saves made before quizzes existed have no `scores` map and count every score as zero.

The `reveal` StoryNode has exactly one choice whose outcome is `{kind: "reveal", results}`, with no condition or cost. Clicking it sends only the choice ID; the server reads the persisted scores and moves to the result with the most points, a tie going to the result listed first. Validation rejects a reveal outcome on any other StoryNode type, a repeated `scoreId`, fewer than two results, or a result that is not an ending, because a result closes the quiz and is what the player shares.

A result StoryNode is any ending a reveal can lead to (`isResultStoryNode` in the domain). The player API returns `result: true` on those StoryNodes. The StoryNode then reads **YOUR RESULT**, the completion shell offers **Take the quiz again**, and the share panel becomes **Share your result** ("I got *The Keeper* in …"). Link previews for seeded quizzes use the same wording, and a shared result link tells the visitor a friend got that result.

## Prototype format change

The node-only model and implicit video fallback were removed. Fixtures publish `story-nodes-v1`; the seeder promotes only known `v1` sample catalogue/branch/published pointers. It never mutates an existing immutable version or deletes accounts/saves. Pre-StoryNode saves are unsupported and show a start-new-journey message; no compatibility renderer is retained. Later StoryNode editions remain version pinned. Reseeding identical versions is safe.

Run `pnpm seed` with emulators, then `pnpm dev:emulator`. For the shared project use `pnpm seed:firebase` with the configured server credential. Run `pnpm check`, `pnpm test:integration`, `pnpm test:story-nodes` and `pnpm test:browser` against emulators. The StoryNode browser check covers desktop/mobile, mixed-media navigation and dice persistence after reload. Domain tests force both roll outcomes; API tests reject forged values and replay the same receipt.

These are server-only snapshots and do not alter any type's completion trigger, output destinations, renderer or condition behavior. Dice binds only on Next.
